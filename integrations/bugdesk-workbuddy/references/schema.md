# 本地建议协议

该技能需要正在运行的新版 BugDesk。用户在 BugDesk 开启 WorkBuddy 连接，提示提供本地连接文件路径；无需 Python、Node 或禅道账号。优先显式使用 Windows PowerShell 5.1：

```powershell
powershell.exe -NoProfile -File '<技能目录>\scripts\bugdesk.ps1' -Action context -ConnectionFile '<用户提示中的连接文件>'
powershell.exe -NoProfile -File '<技能目录>\scripts\bugdesk.ps1' -Action stage -ConnectionFile '<用户提示中的连接文件>' -InputFile '<本地UTF8建议JSON>'
```

将实际路径作为独立参数传入。表格内容写入 JSON 文件，不插入命令行。

已安装且获准使用的 PowerShell 7 可以将上述 `powershell.exe` 换成 `pwsh`；脚本同时接受两版 JSON 解析器产生的整数类型，不接受浮点数或字符串形式的 schema/摘要计数。

保持公司的 PowerShell 执行策略。脚本被策略拦截时报告限制，使用公司批准的执行方式；不要设置全局策略或添加 Bypass。

## 连接与上下文

连接文件由 BugDesk 创建，包含 `schema:1`、`url`、`instance`、`token`、`expires_at`。地址必须是 `http://127.0.0.1:<端口>/`；不能换成公司地址或远程地址。文件和 token 仅在本机使用，不复述或上传。`expires_at` 是带时区的 ISO 8601 字符串。

脚本先读取 `/health`，确认 `app=BugDesk` 和 `instance` 一致，再读取 `GET /api/workbuddy/context`。仅后一个请求携带 `X-BugDesk-WorkBuddy-Token`。上下文提供 `context_id` 及当前批次的草稿资料；以实际响应的 ID 为准，不自行生成或使用上一批的 ID。

网络 JSON 响应最多 8 MiB，用于读取包含多条完整草稿的上下文；超过时明确停止，不截断事实。该额度不扩大建议输入限制：连接文件、建议 JSON 文件和 `stage` 请求仍各限 1 MiB。

## 暂存输入

`POST /api/workbuddy/stage` 接收以下 UTF-8 JSON。文字字段均为字符串，可以留空；换行使用 JSON 转义或 JSON 序列化保留。`candidate_bug_ids`、`source_actual`、`review_notes`、`source_cases` 可省略。未提供 `source_cases` 的旧版 1.0.0 单用例输入继续兼容；多用例归并需要 BugDesk 1.1.0 或更高版本，以及相同版本的配套技能。

```json
{
  "context_id": "从本次context响应取得",
  "rows": [
    {
      "case_id": "PD10000-CA10002",
      "title": "全程语音控制",
      "group": "示例用例/1.0版本/示例播放器",
      "tester": "示例测试员",
      "date": "10月13日",
      "preconditions": "视频播放过程中",
      "steps": "1.语音：先别播了",
      "expected": "1.播放暂停",
      "actual": "会返回到上一界面",
      "source_actual": "【厂商差异】【1.0需求版本】【示例播放器】会返回到上一界面",
      "review_notes": [],
      "suggested_bug_id": "从context草稿取得的唯一对应ID",
      "match_reason": "用例及草稿都记录语音‘先别播了’后返回上一界面。",
      "candidate_bug_ids": []
    }
  ]
}
```

没有唯一匹配时，`suggested_bug_id` 留空，在候选数组列出现有草稿 ID，理由说明需用户确认，不新建 Bug。单用例时 `title` 是原用例名称，多用例时为场景摘要，均不改写 Bug 标题。空的 `actual` 必须由用户补充事实。

一次 1–300 条整理建议，JSON 文件和请求各不超过 1 MiB。四项事实每项最多 20,000 字；用例 ID、人员最多 200 字，名称 1,000 字，分组 2,000 字，日期 100 字，匹配理由 1,000 字。每条建议最多列出 20 个候选 Bug ID；候选过多时说明无法缩小范围，不能随意选定一条。输入不包含附件路径、状态、优先级、审核标记或提交命令，所有层级均仅接受列出的字段。

`source_actual` 是原始失败备注，最多 20,000 字；`review_notes` 是待确认事项的字符串数组，最多 20 条，每条最多 2,000 字。它们只供核对，不填入 Bug 的实际结果。对新版协议不兼容时先提示更新 BugDesk，不把待确认事项塞回 `actual`。

## 一个 Bug 对应多条失败用例

WorkBuddy 先按原始备注形成候选组，再结合 Bug 标题（通常等于证据文件夹名）及每条用例的模块、版本、触发动作和异常现象判断关联。备注相同是强线索，备注与标题不需要逐字一致。近似备注可以语义判断，但必须解释输入中的对应依据；仅有相同管理标签、泛化“失败”或相似标题不能合并。场景都出现同一现象也不能断言共同根因。归属矛盾或未知时保持待核对，不能捏造 Bug ID 或新建 Bug。

同一个已匹配 Bug 最多一个建议。WorkBuddy 完成组合与报告整理，用户只核对报告；不要逐条暂存让用户多选组合。按事实差异归类，不按来源用例数量拆场景。前置条件、操作流程、预期和实际相同，仅 query 或参数不同，写一套公共前置条件与步骤，并列出完整输入清单，每个 query/语音原句一行一条或紧凑列出，共同预期和实际各写一次；不能为二十条相似用例重复写二十个场景，也不能只列代表样本加“等”遗漏输入。确有条件、流程、预期或实际差异时才分组，例外单列，保留每个具体输入与其特有预期、实际的对应。独立操作不能拼成连续步骤，不编造共同操作、重置动作或顺序依赖。缺失或矛盾写进 `review_notes`，缺少事实的对应正文留空，不从预期推测实际，也不从相同备注推断所有输入都出现未记录的现象。所有原始用例仍完整放入 `source_cases`。

多来源建议在顶层保留完整、已整理的四项事实，增加 `source_cases` 供来源对照。顶层 `case_id` 建议留空，`title` 为场景摘要；不要拿某个代表 ID 伪装全部用例。每个来源对象必须有 `case_id`、`title`、`group`、`tester`、`date`、`preconditions`、`steps`、`expected`、`actual` 字符串，可选 `source_actual`，不接受其他字段；来源中保留每条用例的原始 ID、名称、事实和备注。元数据和四项长度限制与顶层相同，`source_actual` 最多 20,000 字。来源事实只供对照，不能直接替代顶层已归并的四项正文；顶层 `source_actual` 可写共同原备注，不同备注则分场景保留。

`source_cases` 必须为 1–300 项的数组，不接受空数组或单个对象。整次请求的来源用例累计最多 300 条：有 `source_cases` 的建议按其长度计数，无该字段的旧建议按 1 条计数。JSON 总计仍受 1 MiB 限制。来源事实和原始备注暂存于内存供预览；导入后草稿保存 `case_sources` 元数据数组，同时以首项 `case_source` 兼容旧数据，保留每条原始用例的 ID、名称、分组、人员和日期。多来源建议始终需要人工核对 AI 关联，不因一个代表 ID 变成精确匹配。

例如两个 query 的原备注都是“【示例版本】讲故事后设备仍播报故事”，文件夹标题是“儿童模式外不合适的故事仍被播报”，可在核对语义与事实吻合后发送一个建议：

```json
{
  "context_id": "本次上下文ID",
  "rows": [{
    "case_id": "",
    "title": "儿童模式外的两个故事请求场景",
    "group": "示例/故事",
    "tester": "",
    "date": "",
    "preconditions": "已绑定设备，当前不在儿童模式。",
    "steps": "语音发出以下故事请求，观察设备响应。\n输入清单（各自为独立用例）：\n• 讲个恐怖故事\n• 讲个鬼故事",
    "expected": "上述两个请求均不播报所请求的故事。",
    "actual": "上述两个请求后，设备均仍播报故事。",
    "source_actual": "【示例版本】讲故事后设备仍播报故事",
    "review_notes": [],
    "suggested_bug_id": "本次上下文中的目标Bug ID",
    "match_reason": "两条原始备注相同；两个具体故事请求的操作、实际现象均与该文件夹标题描述的问题对应。未推断共同根因。",
    "candidate_bug_ids": [],
    "source_cases": [
      {"case_id":"DEMO-CA1","title":"请求恐怖故事","group":"示例/故事","tester":"","date":"","preconditions":"已绑定设备，当前不在儿童模式。","steps":"语音：讲个恐怖故事","expected":"不播报恐怖故事","actual":"【示例版本】讲故事后设备仍播报故事","source_actual":"【示例版本】讲故事后设备仍播报故事"},
      {"case_id":"DEMO-CA2","title":"请求鬼故事","group":"示例/故事","tester":"","date":"","preconditions":"已绑定设备，当前不在儿童模式。","steps":"语音：讲个鬼故事","expected":"不播报鬼故事","actual":"【示例版本】讲故事后设备仍播报故事","source_actual":"【示例版本】讲故事后设备仍播报故事"}
    ]
  }]
}
```

## 实际结果的整理

按失败用例的步骤理解触发动作，以备注中明确记录的现象为依据，组织自然、独立可读的结果描述。保留测试含义，不需要逐字复制备注。只有预期结果或“失败”状态而没有现象时，留空并在 `review_notes` 请求补充。

- 失败备注：`【厂商差异】【1.0需求版本】【消息订阅】删除修改过的消息订阅播报任务，会重新生成修改前的任务`。可写 `actual`：`删除已修改的消息订阅播报任务后，列表中重新出现修改前的任务。` 若步骤只有点击删除、点击确定，没有修改过程，在 `review_notes` 写“备注提到已修改的任务，但步骤未记录修改过程，需确认修改内容及发生时间”；不能擅自补进复现步骤。
- 备注 `唤醒后页面提示【设备离线】` 中的括号是界面提示，应保留为 `唤醒设备后，页面提示【设备离线】。` 管理标签和产品界面文字需要按上下文区分，不能一律删除括号。
- 备注只有 `失败，具体响应未记录` 时，`actual` 留空，`review_notes` 说明需要补充设备响应；不能根据“应进入页面”的预期自行写“未进入页面”。

成功响应包含 `plan_id` 和 `summary`，计数为 `total`、`exact`、`suggested`、`unmatched`。脚本只返回这些摘要及“已暂存，请回 BugDesk 核对并填入”；不会把服务响应里的其他内容回显。上下文过期或草稿发生变化时，重新执行 `context`，重新理解和核对后生成新的建议；不要自动重试旧建议。

## 生效位置

`stage` 只暂存待核对建议。草稿的填入、覆盖确认、审核、附件处理和提交仍由用户在 BugDesk 完成。默认只补空白；对于包含多条来源的建议，如果合并报告的任一非空事实与已有非空正文不同，整次导入会拒绝，提示核对后勾选“覆盖已有内容”，避免只更新来源却漏掉新增场景。只补空白或完全相同的重复导入仍按原规则处理，单来源行为不变。此技能包的创建不表示已经安装到用户公司的 WorkBuddy，也不表示已连接共享文档。
