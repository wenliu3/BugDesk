# BugDesk local application contract

Windows local tool. Python standard library HTTP server (loopback only), buildless vanilla HTML/CSS/JS UI. No CDN, no remote services, no framework. Files under web/ are packaged in the executable. User data stays in local app storage, never in the bug folders.

## HTTP API
All responses are JSON unless noted. Errors use {error: Chinese human-readable message}. GET /api/state returns complete state. POST mutations require X-BugDesk-Token from GET /api/bootstrap ({token, version, data_dir, connection}). Native folder chooser POST /api/pick-folder -> {path} (empty if cancelled). POST /api/scan {path, demo?: boolean} -> state. POST /api/save {bugs?: [{id, ...editableFields}], settings?: {...}, profiles?: [...], active_profile?: string} -> state. POST /api/demo {} -> state. POST /api/export {format: "markdown"|"json"|"csv"} -> {path, filename, url}. GET /api/download?file=opaqueID downloads generated exports. POST /api/open-folder {bug_id?: string} opens selected bug's folder or current date folder. GET /api/attachment?bug_id=...&attachment_id=... serves only known in-batch attachments, with Range support. POST /api/shutdown {} shuts down after response.

## State

UI-only POST `/api/scan/preview` accepts `{path}` and returns an expiring `plan_id`, `root_dir`, `batch_key`, `targets:[{folder_name,folder}]` and `sources:[{source_batch_key,bug_id,title,original_title,old_folder,source_root,status,remote_id,review_token,settings_note}]`. Only saved records whose old directories are actually missing are candidates; permission errors and links are not evidence of a move. No records or files change at preview. Counts/notices disclose truncated previews. UI choices default to new Bugs and never infer ownership from similar titles. A user may explicitly match unique identical original folder names within one selected source batch and then review the mappings.

POST `/api/scan` additionally accepts `relink_plan_id` and `relinks:[{folder_name,source_batch_key,bug_id,review_token}]`. All explicit mappings must be unique, reference the server preview's new targets and missing sources, come from one source batch, and retain the store and target-tree snapshots. Expired/changed previews are rejected atomically. A successful relink preserves stable Bug identity, edited title, facts, provenance, lifecycle and ZenTao IDs, moves only the local record out of its previous batch, updates the folder/original folder name, and rescans attachments. Empty destination batches inherit the source public settings; existing destination public settings remain and migrated Bugs preserve their original effective values in per-Bug overrides. Demo batches cannot become real through relinking. Evidence files are never renamed, moved or deleted. Unselected folders follow normal new-draft scanning.

WorkBuddy draft intake is enabled by the UI through POST `/api/workbuddy/enable` and disabled through POST `/api/workbuddy/disable`. These UI mutations require the existing UI token. A separate 60-minute capability in the local `workbuddy-session.json` authorizes only GET `/api/workbuddy/context` and POST `/api/workbuddy/stage` using `X-BugDesk-WorkBuddy-Token`. Context returns editable draft IDs, names, source IDs, four facts and attachment names, without paths, credentials, settings or submission history. Context snapshots and pending suggestions are in memory, bound to the current batch and draft review tokens. Stage accepts `{context_id,rows:[{case_id,title,group,tester,date,preconditions,steps,expected,actual,suggested_bug_id,match_reason,candidate_bug_ids?,source_actual?,review_notes?,source_cases?}]}` (1 MiB total, 300 rows, 20k per fact). The server assigns row IDs and distinguishes actual unique ID links from AI suggestions. GET `/api/workbuddy/status` returns enabled state and pending suggestions for the UI. An optional `known_plan_id` returns `{plan_id,unchanged:true}` for the same plan without cloning facts or recomputing review tokens.

UI-only POST `/api/workbuddy/apply` takes `{plan_id,assignments:[{row_id,bug_id,mode}],review_scope?:"bugs"}`, loads original pending facts and review tokens server-side, and reuses atomic draft application. The current UI uses `review_scope:"bugs"`: the left pane lists pending Bugs, each Bug chooses one already-composed suggestion (which may contain multiple source cases), and progress counts Bugs rather than source rows. Users review the report and its sources; they do not assemble the grouped cases themselves. A successful partial apply completes the selected Bug targets, retaining all source rows and stable row IDs for use by other Bugs, including Bugs without an initial match. The new pending plan excludes completed Bugs and removes their suggested/candidate references. Responses include `total_bugs`, `remaining_bugs`, `remaining_cases`, cumulative `completed_bug_ids`, `remaining` (the Bug count) and `pending`; `remaining_cases` retains the legacy count of pending suggestion rows, while the UI can separately total all underlying source cases. A partial pending plan carries those counts and `review_scope:"bugs"`. Subsequent applies inherit that scope when omitted. When all Bugs are complete, pending becomes null and both remaining counts become zero. Legacy callers that omit scope on a new plan keep the previous behavior: selected source rows are consumed, `remaining` counts source rows, and unconsumed source facts remain available. Both modes rebase only against their own successful post-write state and issue a new plan ID. External edits to pending Bugs still invalidate snapshots; completed Bugs no longer participate in the pending snapshot. It never reviews or submits. A changed batch, rescan requirement, expiry, disabling or normal shutdown retires the capability and its local file. The skill helper is Windows PowerShell 5.1/PowerShell 7 compatible and supports only context/stage; this separation prevents accidental use of UI mutation endpoints, not arbitrary local-process sandboxing.

Optional `source_cases` is a strict array of 1–300 source objects with `{case_id,title,group,tester,date,preconditions,steps,expected,actual,source_actual?}`. The helper requires the listed string fields (empty strings allowed), and both helper and server reject unknown keys, invalid types, NULs and over-limit text. Metadata limits are case ID/tester 200, title 1000, group 2000, date 100; all four facts and optional original remark are at most 20k characters each. Across one stage request, the sum of source array lengths plus one per legacy row without an array must be at most 300, independently of the existing 300-row and 1 MiB bounds. Missing `source_cases` keeps legacy 1.0.0 single-case behavior; grouped intake is released with BugDesk and its companion skill 1.1.0. Nested original facts are preview-only and must never replace the composed top-level four facts. Applying a grouped suggestion stores bounded `case_sources` metadata for all sources and its first item as compatible `case_source`; raw source facts and original remarks stay in the pending preview. Multiple sources never acquire exact linkage merely from a representative top-level ID; single-source exact matching uses the original source ID.

The WorkBuddy skill first groups by original failed-case remarks, then validates each scene against the existing Bug title (usually the evidence folder name), module/version, triggering action and observed failure. Remarks need not equal the Bug title verbatim. Identical substantive remarks are strong evidence; approximate semantic matches require a stated fact-based explanation. Administrative tags, a generic failure marker or similar titles alone never establish a group, and a shared symptom never establishes a common root cause. The skill sends at most one complete suggestion per matched Bug and groups the report by factual differences rather than source-case count. Cases sharing conditions, workflow, expected result and observed result, differing only in queries or parameters, use one common set of conditions and steps plus the complete verbatim input list; common expected and actual results appear once. It must not repeat twenty equivalent scenes or omit inputs behind representative samples and “etc.” Only genuine condition, workflow or result differences create separate groups; exceptions retain their particular input-to-result mapping. Independent cases never become a continuous sequence, and the skill must not invent common actions, resets or ordering dependencies. It preserves all source cases in `source_cases`, places conflicts/missing information in `review_notes`, does not invent observations or infer unrecorded behavior for every input from shared remarks, and leaves uncertain ownership unmatched with candidates rather than creating new Bugs.

For a WorkBuddy suggestion with more than one source case, default `fill` atomically rejects the entire apply if any composed nonempty fact differs from an existing nonempty fact. The UI asks the user to review the complete report and select replace/“覆盖已有内容”; source metadata cannot be updated while silently omitting additional scenes from the report. Filling empty fields, identical repeats and single-source suggestions retain their existing behavior.

The UI shows a before/after comparison reflecting the selected fill/replace mode, including retained facts and updated provenance; empty incoming facts never erase existing facts. Replacing nonempty facts opens a confirmation showing changes for every selected Bug before applying. Changed lines are highlighted using text-only DOM nodes.

Each WorkBuddy apply that changes drafts atomically stores one latest local undo transaction alongside the draft store. Only the four original facts and source metadata are snapshotted, with post-write content/evidence/submission guards. No-change applies preserve the previous transaction. Status and apply responses expose `undo:{transaction_id,count,titles,available,reason}` or null; original snapshots are never exposed to the restricted AI context or public backup state. UI-only POST `/api/workbuddy/undo` accepts `{transaction_id}` and works even without an active WorkBuddy connection. It restores all changed targets in the transaction atomically, clears their reviewed flags, and retains titles, selection, settings, attachments and submission records. A changed batch, facts/settings/evidence, later submission activity, stale transaction or locked target rejects the whole undo. Selection/review changes alone are allowed. Undo persists across restart, invalid optional journals do not discard valid drafts, external backup undo histories are ignored, and write failures roll back memory. Success returns `{state,undone,undo:null,pending:null}`, clears old WorkBuddy proposals/contexts and retains any live connection.

Clipboard testcase intake uses POST `/api/cases/preview` with `{text,html?,mapping?,has_header?}` to parse pasted rows without writing drafts. It returns format, columns, mapping, logical rows with stable row IDs, active batch key, target draft snapshots/review tokens and unique case-ID linkage suggestions. POST `/api/cases/apply` reparses the same input and accepts `{batch_key,assignments:[{row_id,bug_id,review_token,mode:"fill"|"replace"}]}`. Import is atomic, cannot target a different batch, stale/locked/submitted drafts, or duplicate Bug targets. It changes only explicitly associated existing scanned drafts' preconditions/steps/actual/expected and bounded `case_source` metadata. Titles, shared settings, attachments and submission records are preserved. Fill is the default; replace requires the UI checkbox. Changed facts/source invalidate review; identical repeats are unchanged. Rows are not guessed by order or duplicate testcase titles. Clipboard HTML stays in memory and is parsed as data; raw HTML is never inserted into the DOM or persisted.

Clipboard formats include HTML tables, quoted TSV and unquoted multiline TSV with explicit case-ID row boundaries. Header labels identify fields; multiline annotated headers preceding the demonstrated 16-column PD…-CA… records are reconstructed only when the header explicitly identifies the leading case ID, steps and expected columns. Empty extra right-edge padding is ignored without dropping nonempty cells. Headerless 16-column records use the demonstrated profile with an explicit warning to verify column mapping. Other layouts need the mapping controls. Ambiguous or malformed data is rejected rather than split into invented cases. Intake bounds: 1 MiB source, 300 logical rows, 80 columns, 20,000 characters per cell. Each Bug may retain `case_source:{case_id,case_title,group,tester,date}` for compatible single-source matching and local display/search; grouped WorkBuddy intake additionally retains all source metadata in `case_sources` with the first item exposed as `case_source`. These external IDs are not ZenTao case IDs.

Shared settings also include `feedbackBy:""`: an optional plain-text feedback person, at most 100 characters, separate from the login-derived ZenTao creator. Old drafts default to blank. Profiles, backups, previews and exports preserve it; changing it invalidates review. The connector posts `feedbackBy` and verifies a configured value from the created Bug detail.
{version:1, root_dir:string, batch_key:string, scanned_at:string, demo:boolean, settings:{product:"", product_name:"", project:"", project_name:"", execution:"", execution_name:"", module:"0", module_name:"", openedBuild:[], build_name:"", assignedTo:"", assignee_name:"", type:"codeerror", severity:"3", pri:"4", probability:"", os:"", title_prefix:"", preconditions:"", steps_template:"", zentao_url:""}, profiles:[], active_profile:"", bugs:[], warnings:[], history:[]}

Bug fields: {id, folder, original_title, title, preconditions:"", steps:"", actual:"", expected:"", overrides:{}, attachments:[{id,name,path,size,mime,mtime_ns}], excluded_attachments:[], selected:true, reviewed:false, status:"draft", remote_id:null, remote_url:"", error:"", upload_status:{}, updated_at:"", review_token:"dynamic SHA256"}. Status is derived from content: draft when missing title/steps/actual/expected; ready when all present and reviewed; needs_review when complete but not reviewed; submitting/submitted/uncertain/failed/partial for connection lifecycle. Attachment IDs hash relative paths. actual must initially be empty, optional explicit "标题填入实际结果" UI button; no fabricated facts. Changing content or shared settings clears reviewed flags. Review confirmation must send review_token captured when opening the review; stale facts are rejected. Rescan preserves edits and submission results by canonical folder identity, updates attachment list; missing folders no longer active but retained in batch storage.

## Connector API (root server adapts connector implementation)
POST /api/connect {url, account, password} -> {connected:true, message, options:{products:[],users:[]}}. Credentials remain in memory. POST /api/disconnect -> status. POST /api/options {product,project?,execution?} -> {products?,projects:[],executions:[],modules:[],builds:[],users?:[],probabilities?:[]}. Options format [{value:"id", label:"name"}]. Support manual values if company menus fail; shared settings UI supports manual IDs/names.

Options also include `priorities`, read from the actual `pri` select. Public settings, individual overrides, editor badges and report previews use these observed labels/values when available; offline labels are 1=高, 2=中, 3=低, 4=极低, matching the user's company menu. Existing draft/profile codes are preserved rather than silently remapped. Before creating a Bug, a populated observed priority menu must contain the selected value; otherwise creation stops before posting.

GET /api/state also includes session-only `options` and `options_context:{product,project,execution}`. A successful menu read replaces contextual menus, caches only public choices/warnings, and never persists authentication or raw form data. Reconnecting replaces the old cache; disconnecting clears it. The UI restores only matching contexts and ignores stale asynchronous reads. Remote menu controls are searchable; openedBuild is a checkbox multi-select.

Probability discovery also supports a directly captioned repurposed `browser` / `browser[]` select, retaining the observed field key for multipart posting and stripping `[]` only for detail lookup. A browser name or probability-looking choices alone do not establish meaning. On discovery failure, options may include `probability_diagnostic`, a bounded sanitized field summary for explicit local copying; it is never persisted or transmitted automatically and excludes hidden fields, credentials, cookies, raw HTML, and identity menus.

POST /api/submit {ids:[...]} starts background job, refuses demo mode/unconnected/incomplete/unreviewed/already-created/uncertain items. Returns {job_id}. GET /api/job -> {running:boolean,total,done,current_title,results:[{id,status,remote_id,remote_url,error}],cancel_requested:boolean}. POST /api/cancel-submit {} stops before next item (does not pretend to cancel in-flight POST). State is persisted before each network write, status submitting marks ambiguous interruption as uncertain on restart; uncertain never auto-retries. Successful IDs persist and cannot be resubmitted. Connector must return bug ID and attachment confirmation, otherwise status uncertain/partial and user needs to verify on company site. The first actual run limited to one bug until locally recorded confirmed successful creation/upload. UI discloses company integration not yet verified.

## UI requirements

The header provides a moon/sun appearance toggle. Light and dark themes cover the workbench, all dialogs, WorkBuddy review and the guide chrome; original evidence and guide screenshots retain their colors. Initial appearance follows the system until a manual choice. The browser retains the choice using a non-sensitive host-only theme cookie (across random local server ports), with localStorage as a fallback. Theme changes never call draft/settings save APIs or invalidate review.
Polished Chinese app "BugDesk · Bug 提交助手", cool light workspace, teal primary action, inline SVG icons, generous readable space. One compact header contains the brand, a folder popover (path input, browse, scan and open original folder), WorkBuddy, public settings, connection and a more menu (case paste, export, help, shutdown). A two-pane workspace places the search/filter Bug list beside a spacious white editor. Counts live in filter buttons instead of dashboard cards. Keep complete Bug titles editable and preserve bracketed title text; only processing status appears alongside the editor breadcrumb. Shared metadata such as build, severity and priority belongs in public settings and the submission preview, with per-Bug exceptions in a collapsed disclosure. Description fields, attachments with image/video preview, merged report preview, connection, review and export remain available. Header popovers close on outside click or Escape, and only one opens at a time. Auto-save debounce with flush before navigating/scanning/export/submission; keyboard Ctrl+S save, Ctrl+Enter review current, Alt+Up/Down adjacent. Friendly empty state and demo dataset. Explicit demo badge and demo submissions disabled. Responsive horizontal two/three panel desktop and mobile stacked. Use settings IDs only in connection/advanced settings, main workbench uses names. Preserve editor focus/caret during typing. Bulk "mark reviewed" must show all selected formatted descriptions for confirmation, never blindly mark via one click. On close, save pending changes and offer server close button. Always render user text as text, never innerHTML unsanitized.

Asynchronous UI saves retain an in-flight counter for close protection; failed saves restore pending patches without discarding newer edits. Ordinary draft saves reject edits to submitted/uncertain/partial or remote-ID records, while selection remains editable. Company menu I/O uses a separate connector lock and request revision, keeping local saves and disconnects responsive and discarding stale replies. The Skill request/input bound remains 1 MiB, while network responses have a separate 8 MiB bound.

The WorkBuddy bridge accepts optional `source_actual` (20k characters) and `review_notes` (up to 20 strings of 2k characters) on staged rows. They remain preview-only and are not copied into Bug facts. The bridge conservatively removes recognized leading administrative tags and standalone `【待确认】`/`【待补充】` lines from legacy actual text, retains the original for comparison, and preserves unknown/product brackets. The Skill composes an observed-result narrative from supplied failure evidence without inventing observations.
